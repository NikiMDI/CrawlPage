# Памятка для защиты crawler

## Какие goroutine существуют

`Inspector.Crawl` запускает ровно `Config.Concurrency` worker-goroutine. Scheduler не запускается отдельно: его цикл выполняется в goroutine вызывающей функции `Crawl`.

Каждый worker последовательно обрабатывает одно логическое задание и его redirect-цепочку. Crawler не создаёт goroutine на каждый найденный URL, поэтому количество собственных goroutine ограничено.

`net/http` может иметь внутренние служебные goroutine транспорта, но число одновременно начатых crawler HTTP-операций ограничено worker pool.

## Кто создаёт workers

Workers создаёт `Inspector.Crawl`:

```text
for i = 0; i < Concurrency; i++
    WaitGroup.Add(1)
    go runWorker(...)
```

Каждый worker вызывает `Done` через `defer`.

## Как workers получают работу

Scheduler отправляет `crawlTask` в небуферизованный канал `jobs`. Задача содержит URL, глубину и номер выдачи.

Worker получает задачу, вызывает `inspectURL` и отправляет `crawlWorkerResult` в буферизованный канал `results`.

## Как ограничивается concurrency

Ограничение обеспечивается двумя условиями:

1. создано ровно `Concurrency` workers;
2. scheduler выдаёт задания только пока `active < Concurrency`.

Worker не создаёт дополнительные goroutine для запросов и синхронно выполняет максимум один `inspectURL`.

## Где хранится очередь

Очередь находится в поле scheduler:

```go
frontier *list.List
pending  map[string]*list.Element
```

Это ограниченный LIFO-стек. `MaxQueue`/`--max-queue` задаёт максимум URL, ожидающих выдачи worker. `pending` не позволяет одному нормализованному URL занять несколько мест и позволяет обновить его глубину без добавления дубликата. Дочерние ссылки добавляются в обратном порядке, поэтому первая ссылка документа извлекается первой.

Канал `jobs` небуферизован: он только передаёт задание готовому worker и не является второй скрытой очередью. Поэтому одновременно выполняется не более `Concurrency` заданий, ожидает не более `MaxQueue`, а суммарно в работе находится не более `Concurrency + MaxQueue` заданий.

Если `frontier` заполнен, scheduler не блокируется: ссылка отмечается как пропущенная по лимиту очереди. При повторном обнаружении после освобождения места она может быть поставлена в очередь. Сводка показывает лимит, фактический пик и число оставшихся пропущенных URL.

При `Concurrency=1` получается строгий DFS. При большем значении это DFS-приоритет: несколько приоритетных ветвей выполняются параллельно.

## Где хранится visited

Состояние посещения разделено:

- `DepthByURL` — минимальная обнаруженная глубина;
- `running` — URL сейчас выполняется;
- `completed` — URL уже имеет готовый `PageResult`;
- `unavailable` — ответ определён как расходующий бюджет, но не принят из-за `max-pages`;
- `expandedAt` — минимальная глубина, с которой уже расширены дети.

Физические HTTP URL дополнительно хранятся в `crawlSession.cache`. Это нужно потому, что логическая страница и redirect-цепочка могут прийти к одному target.

## Как синхронизирован доступ

Scheduler — единственный владелец `frontier`, `running`, `completed`, `DepthByURL`, `expandedAt` и `CrawlResult`. Workers не изменяют эти структуры, поэтому mutex для графа не нужен.

Workers совместно используют только `crawlSession`. Его cache, `pagesChecked` и `maxPagesReached` защищены одним `sync.Mutex`.

Сетевой запрос выполняется без удержания mutex, поэтому разные URL остаются параллельными.

## Почему один URL не запрашивается дважды

Есть два уровня защиты:

1. scheduler не создаёт повторное логическое задание для `running` или `completed` URL;
2. fetch-кэш создаёт одну `fetchEntry` на нормализованный HTTP URL.

Первый worker становится владельцем запроса. Остальные ждут закрытия `entry.ready` и получают тот же результат.

## Кто определяет завершение

Завершение определяет scheduler.

Crawler заканчивается только когда:

```text
нет runnable URL в frontier
AND
active == 0
```

## Почему программа не завершается слишком рано

Пустой `frontier` сам по себе не завершает обход. Пока `active > 0`, scheduler ждёт worker-result. Полученный HTML может содержать новые ссылки, которые снова заполнят `frontier`.

## Почему программа не зависает после обработки URL

Когда `frontier` пуст и `active == 0`, scheduler возвращает управление. `Crawl` отменяет worker-context, закрывает `jobs` и ждёт `WaitGroup`.

Worker выходит по `ctx.Done()` или закрытому `jobs`. При отправке результата он также выбирает между `results` и `ctx.Done()`, поэтому не остаётся заблокированным отправителем.

## Как распространяется cancellation

`signal.NotifyContext` преобразует Ctrl+C/SIGTERM в отмену контекста. Контекст передаётся через CLI в `Crawl`, scheduler, workers, singleflight waiters и `http.NewRequestWithContext`.

Глобальная отмена возвращает `context.Canceled`. CLI печатает `crawl cancelled`, возвращает код `130` и не выводит частичный отчёт.

## Как обрабатывается timeout

Для каждого HTTP-запроса создаётся дочерний контекст через `context.WithTimeout`.

Если истекает только request timeout, URL получает `ResultKind=TIMEOUT`, добавляется как проблема, а crawler продолжает работу.

Если отменён родительский контекст, прекращается весь обход. Это не записывается как проблема сайта.

Timeout охватывает и получение заголовков, и чтение тела, потому что один request context действует до закрытия `response.Body`.

## Как устроен redirect

Используется `http.RoundTripper`, а не автоматическое следование `http.Client`.

Для каждого ответа 3xx crawler:

1. сохраняет URL и HTTP status;
2. читает `Location`;
3. разрешает относительный адрес через `net/url`;
4. проверяет принадлежность scope, включая разрешённый HTTP→HTTPS upgrade;
5. проверяет redirect-cycle;
6. проверяет `MaxRedirects`;
7. сам запрашивает следующую внутреннюю цель.

Поэтому отчёт не теряет промежуточные переходы.

Внешняя redirect-цель записывается, но не запрашивается.

## Как обнаруживается цикл

Для обычного графа цикл прекращается состояниями `running/completed` и минимальной глубиной `DepthByURL`.

Например, при A → B → C → A повторный A не запрашивается, потому что A уже completed с меньшей глубиной.

Для redirect-цепочки используется отдельное множество `redirectURLs` внутри одного `inspectURL`. Если следующий URL уже встречался в этой цепочке, устанавливаются:

```text
ResultKind = REDIRECT_ERROR
RedirectCycleDetected = true
```

## Зачем нужны `Depth` и `FetchDepth`

`FetchDepth` — глубина, на которой HTTP-запрос фактически был запущен.

`Depth` — минимальная глубина, найденная после исследования графа.

При конкурентном обходе URL может стартовать на глубине 3, а затем быть найден на глубине 2. Повторного HTTP-запроса нет, но `Depth` уменьшается, а сохранённые ссылки повторно расширяются через `expandedAt`.

## Что ограничивает `max-pages`

`max-pages` ограничивает количество принятых page-like результатов: HTML, redirect и ошибок. Решение принимается после получения HTTP-заголовков, когда уже известны статус и `Content-Type`; проверка и `pagesChecked++` выполняются атомарно под mutex.

`MaxPagesReached=true` означает, что из-за исчерпанного бюджета был отклонён хотя бы один новый URL. Одного равенства `PagesChecked == max-pages` недостаточно, если следующего кандидата не существовало.

HTML, `HTML_TOO_LARGE`, redirect hops, timeout, сетевые и HTTP-ошибки расходуют бюджет. Успешный non-HTML-ответ бюджет не расходует; его тело не читается и HTML-парсер не запускается. Тип определяется по `Content-Type`, поэтому правило работает и для `/asset` без расширения. Повторный cached URL и внешний URL бюджет не расходуют. PDF никогда не запрашивается: внутренняя ссылка заранее переносится в `Skipped`, redirect останавливается перед PDF-целью, а PDF запрещён как стартовый URL.

Для определения `Content-Type` запрос должен дойти как минимум до заголовков. Поэтому число диагностических HTTP-запросов может быть больше `PagesChecked`: HTML сверх бюджета закрывается до чтения и разбора body, а успешный non-HTML остаётся бесплатным. Fetch-кэш по-прежнему гарантирует не более одного физического запроса на нормализованный URL.

## Что произойдёт с сайтом из миллиона страниц

`PagesChecked` не превысит `max-pages`, одновременно выполняется не больше `concurrency` запросов, а в `frontier` ожидает не больше `max-queue` URL. Бесконечного создания goroutine и неограниченного роста очереди workers не произойдёт. Диагностических запросов заголовков может быть больше `max-pages`, потому что только ответ сервера позволяет надёжно отличить extensionless `/asset` от HTML.

Однако память зависит не только от числа запросов. Crawler хранит обнаруженные URL, рёбра, источники и содержимое очереди. Если одна разрешённая HTML-страница содержит миллион разных `<a href>`, их всё равно нужно разобрать и записать для отчёта. Память в худшем случае растёт как `O(V + E)` по обнаруженной части графа.

Размер одной HTML-страницы ограничен параметром `MaxHTMLBytes` и CLI-флагом `--max-html-bytes` (по умолчанию 2 МиБ). Crawler читает максимум `limit + 1` байт, поэтому обнаруживает превышение даже без корректного `Content-Length`. Усечённый HTML не разбирается и получает отдельный результат `HTML_TOO_LARGE`, но ответ `200 OK` не попадает в `BROKEN_LINKS`.

Для обхода сайтов значительно больше учебного графа дополнительно понадобились бы:

- предел числа ссылок на одну страницу;
- потоковая или дисковая очередь;
- пакетная запись отчёта;
- ограничение общего числа обнаруженных URL, а не только HTTP fetch;
- сохранение графа во внешней базе.

## Правило области обхода

Внутренней считается HTTP(S)-ссылка с тем же `hostname`. Схема и порт намеренно не сравниваются:

```text
http://example.com:8080 → https://example.com:8443 — INTERNAL
https://example.com → http://example.com:8080 — INTERNAL
https://other.example.com → EXTERNAL
```

Так crawler продолжает обход при смене `http`/`https` и любого порта, пока hostname не изменился. Fragment удаляется, query сохраняется. Относительный URL разрешается относительно первого `<base href>`; если его нет или он не нормализуется, используется конечный URL страницы после redirect. Trailing slash не склеивается с вариантом без slash, потому что сервер может считать их разными ресурсами.

## Что означает `Elapsed`

`Elapsed` — длительность полного `Crawl`: от начала обхода до завершения workers и формирования результата. Время печати отчёта в stdout в него не входит.

## Команды перед защитой

```powershell
go test ./...
go vet ./...
go test -count=20 ./tests/crawler -run "Concurrent|Cancellation|Acceptance"
go test -race ./...
```

На Windows для `-race` требуются `CGO_ENABLED=1` и установленный MinGW-w64/GCC.
