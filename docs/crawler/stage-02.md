# Этап 2. Последовательный обход графа в глубину

На этом этапе crawler обходит внутренний граф сайта алгоритмом DFS. Обход остаётся последовательным: одновременно выполняется не более одного HTTP-запроса, workers и каналы ещё не используются.

## Запуск

В первом терминале запустите тестовый сайт с короткой задержкой, чтобы будущий timeout-сценарий пока не мешал демонстрации DFS:

```powershell
go run ./cmd/graphsite --slow-delay "100ms"
```

Во втором терминале:

```powershell
go run ./cmd/crawler `
  --url "http://127.0.0.1:8080/index.html" `
  --depth 3 `
  --max-pages 100 `
  --timeout "2s"
```

## Алгоритм

```text
start URL (depth 0)
        ↓
положить в LIFO-стек
        ↓
извлечь верхнее задание
        ↓
проверить URL и сохранить страницу
        ↓
извлечь и нормализовать <a href>
        ↓
внутренние новые URL положить в стек
        ↓
        повторять, не учитывая больше max-pages страниц
```

Используется явный ограниченный LIFO `container/list`, а не рекурсивные вызовы Go. Ссылки добавляются в стек в обратном HTML-порядке, поэтому первая ссылка документа извлекается первой. Размер ожидающей очереди задаётся `--max-queue`; активные запросы ограничиваются отдельно параметром `--concurrency`.

## Нормализация URL и граница сайта

Каждый `href` разрешается через `net/url` относительно страницы, на которой он найден. Поэтому одинаково поддерживаются абсолютные URL, `/about`, `../contacts` и `?id=10`.

Перед сравнением и добавлением в граф применяются следующие правила:

- схема и имя хоста приводятся к нижнему регистру;
- стандартные порты `:80` для HTTP и `:443` для HTTPS удаляются;
- пустой путь превращается в `/`;
- fragment (`#section`) удаляется, потому что он не меняет HTTP-ресурс;
- query parameters сохраняются; `/products?id=10` и `/products?id=20` считаются разными URL;
- порядок query parameters не перестраивается;
- trailing slash сохраняется, поэтому `/docs` и `/docs/` считаются разными URL;
- повторный нормализованный URL запрашивается только один раз, но каждое найденное ребро и все разные страницы-источники остаются в результате;
- пустой `href` разрешается в URL текущей страницы и потому не вызывает повторный запрос.

Внутренней считается HTTP(S)-ссылка с тем же hostname. Схема и порт не сравниваются, поэтому переход `http://example.com:8080` → `https://example.com:8443` остаётся внутренним. Другой hostname считается внешним. Ссылки других схем (`mailto:`, `javascript:` и подобные) пропускаются и сохраняются в списке `Skipped` с причиной.

## Состояние обхода

- `DepthByURL` хранит минимальную найденную глубину каждого внутреннего URL;
- `visited` хранит URL, для которых HTTP-запрос уже выполнялся;
- `expandedAt` хранит минимальную глубину, с которой уже распространялись дочерние ссылки;
- `Pages` хранит результаты в фактическом DFS-порядке первой HTTP-проверки;
- `SourcesByURL` хранит все разные страницы-источники каждого нормализованного URL.

Три раздельных состояния нужны из-за графа с несколькими путями. Страница может сначала встретиться по длинному пути, а затем по короткому. Второй HTTP-запрос не выполняется: сохранённые ссылки страницы повторно распространяются из кэша с меньшей глубины.

Поэтому у страницы есть:

- `FetchDepth` — глубина пути, по которому она фактически была запрошена DFS;
- `Depth` — минимальная глубина, найденная после исследования доступной части графа.

Например, `/c.html` сначала проверяется по пути `index → a → b → c` на глубине 3, но позднее ссылка `index → hub → c` уточняет её минимальную глубину до 2.

## Ограничение глубины

- стартовая страница имеет глубину `0`;
- страница с глубиной ровно `--depth` проверяется; ссылки извлекаются, если ответ имеет статус `2xx` и HTML Content-Type;
- её ссылки глубины `--depth + 1` сохраняются в графе, но не запрашиваются;
- внешний URL не получает глубину внутреннего графа и никогда не помещается в стек.

При `--depth 3` ссылка `/deep-target.html` обнаруживается на глубине 4, но HTTP-запрос к ней не выполняется.

## Ограничение страниц

`--max-pages` ограничивает количество принятых результатов страниц. В лимит входят:

- HTML-страницы;
- ответы `3xx`, `4xx`, `5xx`;
- попытки, завершившиеся сетевой ошибкой или timeout.

Успешные non-HTML-ресурсы, внешние ссылки и повторные cached URL лимит не расходуют. Если один URL встретился несколько раз, все рёбра и источники сохраняются, но HTTP-запрос выполняется один раз.

Чтобы определить тип ресурса без доверия к расширению URL, crawler получает HTTP-заголовки. Поэтому сетевых запросов может быть больше `Pages checked`: HTML сверх бюджета не читается и не разбирается, а успешный non-HTML принимается бесплатно.

## Не-HTML ресурсы

Если успешный ответ оказался non-HTML по `Content-Type`, crawler не читает его body, не передаёт содержимое HTML-парсеру и не расходует `max-pages`. Расширение не используется для классификации: одинаково обрабатываются JPG, PNG, MP4, CSS, JavaScript, `application/octet-stream` и `/asset` без расширения. URL, путь которого оканчивается на `.pdf` без учёта регистра, вообще не запрашивается: внутренняя ссылка сохраняется в `Skipped`, redirect останавливается перед PDF-целью, а PDF запрещён как стартовый URL.

## Ожидаемый результат для тестового сайта

При `--depth 3`, `--max-pages 100` и timeout больше задержки `/slow.html` ожидается:

```text
Pages checked:      13
Links discovered:   23
Unique HTTP links:  15
Internal links:     22
External links:     1
```

`Internal links` и `External links` считают вхождения ссылок, а не уникальные URL. Поэтому несколько ссылок на один `/hub.html` учитываются отдельно, хотя сам `/hub.html` запрашивается один раз.

Строгий порядок первых HTTP-проверок:

```text
 1. /index.html
 2. /a.html
 3. /b.html
 4. /c.html
 5. /depth-1.html
 6. /depth-2.html
 7. /depth-3.html
 8. /hub.html
 9. /redirect-once
10. /redirect-chain/start
11. /slow.html
12. /missing-page.html
13. /server-error
```

## Что пока намеренно не реализовано

- HTTP-результаты ещё не классифицируются как `HTTP_4XX`, `HTTP_5XX`, `TIMEOUT` или `NETWORK_ERROR`;
- redirect сохраняется как обычный ответ `3xx`, но `Location` пока не сопровождается;
- нет `--concurrency`, scheduler, workers и каналов;
- нет финальной группировки проблем второго уровня;
- частичный отчёт при `Ctrl+C` появится вместе с полным управлением жизненным циклом.

Ошибка одной страницы сохраняется в строковом поле `PageResult.Error` и не прекращает DFS. Отмена общего контекста через `Ctrl+C` останавливает весь обход.

## Проверка

```powershell
go test ./...
go vet ./...
go test -count=50 ./tests/...
go test "-coverpkg=./internal/crawler,./internal/crawlercli" ./tests/...
```

Все `_test.go` находятся в отдельной папке `tests`. Поскольку в Go каждый каталог является отдельным пакетом, тесты проверяют нормализацию, HTML-парсер и DFS через публичные методы `New`, `InspectStart` и `Crawl`. CLI-логика находится в импортируемом внутреннем пакете `internal/crawlercli`; `cmd/crawler` остаётся только точкой входа приложения.
