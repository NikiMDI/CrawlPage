# Этап 5. Ограниченный конкурентный обход

На пятом этапе последовательный DFS преобразован в crawler с фиксированным worker pool. Количество одновременно работающих HTTP-проверок задаётся параметром `--concurrency`.

## Запуск

```powershell
go run ./cmd/graphsite --slow-delay "100ms"
```

```powershell
go run ./cmd/crawler `
  --url "http://127.0.0.1:8080/index.html" `
  --depth 3 `
  --max-pages 100 `
  --max-redirects 10 `
  --concurrency 4 `
  --timeout "2s"
```

`--concurrency 4` означает, что crawler создаёт четыре worker goroutine. Каждый worker обрабатывает только одно задание за раз, поэтому одновременно выполняется не больше четырёх HTTP-запросов.

## Архитектура

```text
                    ┌───────────────┐
                    │   Scheduler   │
                    │ queue + graph │
                    └───────┬───────┘
                            │ jobs
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
           Worker 1      Worker 2      Worker N
              │             │             │
              └─────────────┼─────────────┘
                            │ results
                            ▼
                    ┌───────────────┐
                    │   Scheduler   │
                    └───────────────┘
```

Scheduler является единственным владельцем состояния графа:

- LIFO-очереди `frontier`;
- минимальных глубин `DepthByURL`;
- состояний `running`, `completed` и `unavailable`;
- информации о последнем расширении `expandedAt`;
- страниц-источников;
- итогового `CrawlResult`.

Workers не изменяют эти структуры. Worker получает логический URL, вызывает `inspectURL`, последовательно проходит его redirect-цепочку и возвращает готовый `PageResult` через канал результатов.

## Ограничение конкурентности

При запуске создаётся ровно `Config.Concurrency` workers. Внутри worker нет дополнительных goroutine для HTTP-запросов. Поэтому верхняя граница одновременно выполняющихся `RoundTrip` равна числу workers.

Scheduler хранит число активных заданий. Новая работа выдаётся, только когда:

```text
active < concurrency
```

Crawler завершается только при выполнении двух условий:

```text
frontier пуст
AND
active == 0
```

Пустой очереди недостаточно: выполняющийся worker ещё может вернуть HTML с новыми ссылками.

## DFS и конкурентность

При `--concurrency 1` сохраняется строгий последовательный DFS из этапа 2.

При значении больше единицы scheduler всегда берёт задания с вершины LIFO-стека, но несколько ветвей могут выполняться одновременно. Это называется DFS-приоритетом:

```text
/a запущена первой, но отвечает медленно
/b запущена второй, но отвечает быстро
```

Порядок завершения таких запросов не обязан совпадать с последовательным DFS. В отчёте страницы сортируются по порядку выдачи заданий scheduler, а не по скорости HTTP-ответов. Корректность глубины, `visited`, лимитов и графа от порядка ответов не зависит.

## Потокобезопасный fetch-кэш

Общий `crawlSession` теперь защищён mutex. Для каждого нормализованного HTTP URL хранится отдельная запись:

```go
type fetchEntry struct {
    ready  chan struct{}
    result fetchedURL
    err    error
}
```

Первый worker:

1. резервирует URL в кэше;
2. атомарно увеличивает `pagesChecked`;
3. отпускает mutex;
4. выполняет HTTP-запрос;
5. сохраняет результат;
6. закрывает `ready`.

Другой worker, которому нужен тот же URL, не выполняет второй запрос, а ждёт закрытия `ready`.

```text
/direct ───────────────→ /target
/old → 302 redirect ───→ /target
```

В этом примере `/target` физически запрашивается один раз, но direct-ссылка и `/old` сохраняют отдельные логические результаты и страницы-источники.

Singleflight охватывает только один HTTP-запрос, а не всю redirect-цепочку. Ответ текущего URL публикуется в кэш до перехода к следующему target. Поэтому пересекающиеся цепочки не создают взаимную блокировку:

```text
/a → /b
/b → /a
```

Оба ответа сначала становятся доступными в кэше, после чего каждое задание обнаруживает цикл в собственном множестве `redirectURLs`.

## `max-pages` при конкуренции

Проверка лимита, создание cache entry и увеличение `pagesChecked` выполняются под одним mutex. Поэтому даже при большом числе workers значение никогда не превысит `MaxPages`.

В лимит входят уникальные URL, для которых реально начат запрос:

- HTML;
- изображения и PDF;
- промежуточные и конечные redirect URL;
- timeout и сетевые ошибки.

Кэшированный URL и внешний redirect target лимит повторно не расходуют.

Если несколько workers одновременно претендуют на последнее свободное место, конкретный URL-победитель может зависеть от планировщика Go. Гарантируются верхняя граница, уникальность запросов и корректное завершение, но не конкретная последняя ветка. Для полностью последовательного DFS-префикса используется `--concurrency 1`.

## Глубина

Если URL уже проверяется на глубине 3, а затем найден путь глубины 2:

- второй HTTP-запрос не запускается;
- `FetchDepth` остаётся равным 3;
- `Depth` обновляется до 2;
- ссылки страницы расширяются относительно минимальной глубины.

`expandedAt` позволяет повторно обработать уже сохранённые ссылки на меньшей глубине без повторного HTTP-запроса.

## Проверяемые сценарии

Тесты этапа 5 проверяют:

- реальный параллелизм и точный предел `Concurrency`;
- строгий DFS при `Concurrency == 1`;
- один запрос для direct URL и redirect target;
- отсутствие deadlock у пересекающихся redirect-циклов;
- атомарный `max-pages` при большом числе workers;
- общий лимит страниц для одновременных redirect-цепочек;
- отсутствие повторных HTTP-запросов;
- совместимость со всеми тестами этапов 1–4.
